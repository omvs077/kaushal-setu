# Kaushal Setu (कौशल सेतु): Software Requirements Specification (SRS / SRD)

*Official Project Name: Kaushal Setu (कौशल सेतु) · Planning Code Name: LMI-NEXUS · SIH PS 26246 · MSDE · Version 1.0 · Status: baseline for MVP build · Follows the structure of IEEE 29148*

## 1. Introduction

### 1.1 Purpose

This document specifies what LMI-NEXUS shall do and the qualities it shall have. It is the contract between the product definition (PRD), the design (UI/UX and architecture) and verification (tests, demo, audit). Every requirement has an ID, a priority and an acceptance criterion so that it can be built, tested and traced.

### 1.2 Scope

LMI-NEXUS is a Labour Market Intelligence System for the Ministry of Skill Development and Entrepreneurship (MSDE), NCVET, Sector Skill Councils (SSCs) and State Skill Development Missions. It aggregates labour demand signals, compares them with training capacity, forecasts district- and sector-level demand-supply gaps, ranks mismatches, raises early-warning flags, recommends seat reallocation, and exposes everything through a multilingual, accessible dashboard and an API/export layer.

| In scope | Out of scope |
| --- | --- |
| Demand, supply and gap forecasting at district × trade × horizon | Individual job matching, candidate recommendation, résumé processing |
| Dashboard, API, exports, alerts, what-if | Training delivery, certification, placement management |
| Data pipeline, quality control, governance, audit | Collecting person-level data; any personal data in analytics |
| Pilot: 3 states, 5 sectors (MVP); national (Full) | Web scraping of job sites; use of generative AI/LLMs in computation |

### 1.3 Definitions

| Term | Meaning |
| --- | --- |
| CDI | Composite Demand Index: fused demand estimate in workers per year, per district and occupation (see Architecture, section 17) |
| NCO-2015 | National Classification of Occupations |
| NSQF / QP | National Skills Qualifications Framework / Qualification Pack (job role) |
| NIC-2008 | National Industrial Classification |
| LGD | Local Government Directory district and state codes |
| Cell | One combination of district × trade (occupation/QP) × horizon |
| Run | One complete, versioned computation producing a published snapshot |
| Parameter set | Versioned, approved coefficients and thresholds used by a run |
| Severity | `(Demand − Supply) / Demand`, clipped to \[−1, +1\]; positive means shortage |
| Horizon | Forecast lead: 3, 6 or 12 months |
| Synthetic | Data generated by the platform for demonstration; always labelled |

### 1.4 References

Official PS 26246 statement; NCO-2015; NSQF; NIC-2008; LGD; PLFS reports; Digital Personal Data Protection Act 2023; IT Act and CERT-In directions (2022); GIGW 3.0; WCAG 2.1 AA; OWASP ASVS and API Security Top 10; Architecture document (Parts I and II); PRD; Design document.

### 1.5 Conventions

- **Priority:** **M** = MVP (hackathon build, must have), **S** = MVP stretch (build if time allows), **F** = Full product.
- **Verification:** **T** = automated test, **D** = demonstration, **I** = inspection/review, **A** = analysis.
- "Shall" is mandatory within its priority tier. IDs are stable; retired IDs are never reused.

## 2. Overall Description

### 2.1 Product perspective

```
 Data owners ──► [ Ingestion + Quality ] ──► [ Forecast engine ] ──► [ Published snapshot ]
 (NCS, e-Shram,        (adapters, validation,    (CDI, Leontief,           │
  dummy dataset,        quarantine, mapping)      gap, flow, MC)           ▼
  public data,                                                        [ API + Export ] ◄── scheme workflows
  telemetry)                                                              │
                                                                          ▼
                                           Planners (MSDE, NCVET, SSC, SSDM) via dashboard
```

LMI-NEXUS is a new standalone system. It reads data from external sources and exports forecasts. It does not write back to any source system.

### 2.2 User classes

| Class | Needs | MVP role |
| --- | --- | --- |
| National Planner (MSDE/NCVET) | National view, cross-state ranking, target packs | Yes |
| State Planner (SSDM) | Own-state drill-down, recommendations, exports | Yes |
| District Officer | Own-district view, alerts | Yes (read-only) |
| Sector Skill Council analyst | Sector-wise view across states | F (use National Planner in MVP) |
| Data Steward | Source health, quality, mappings, uploads | Admin in MVP |
| Model Governor | Parameter approval | Admin in MVP; separate role in F |
| Auditor | Read-only access to manifests and audit log | Yes (read-only) |
| Administrator | Users, configuration | Yes |
| External system | API consumer for target-setting | F (keys); MVP uses exports |

### 2.3 Operating environment

Modern evergreen desktop browsers (primary), tablets (supported), phones (read-only layouts). Server side: Linux containers, PostgreSQL with PostGIS, Redis. Hosting in India. MVP on one VM; Full on Kubernetes.

### 2.4 Constraints

| ID | Constraint |
| --- | --- |
| CON-01 | No web scraping and no generative-AI service in any computation path |
| CON-02 | Analytics uses aggregated data only; no person-level records are stored |
| CON-03 | All runtime assets (fonts, scripts, map data) self-hosted; no third-party calls from the browser |
| CON-04 | Hosting and data storage within India for restricted data |
| CON-05 | Open-source components only; every dependency pinned and scanned |
| CON-06 | MVP built by a team of about six within the hackathon schedule |
| CON-07 | District boundaries must follow the official depiction of India's borders |

## 3. Functional Requirements

### 3.1 Source management and ingestion (FR-ING)

| ID | Requirement | Pri | Acceptance / verification |
| --- | --- | --- | --- |
| FR-ING-01 | The system shall maintain a source registry recording owner, access mode, geography grain, cadence, licence status, adapter and health for each source | M | Registry lists every source used; each run references source IDs (T) |
| FR-ING-02 | The system shall ingest the provided hackathon dataset from CSV/XLSX/JSON through a file adapter | M | Full load with no manual edits; row counts reconcile to the source files (T) |
| FR-ING-03 | The system shall load reference data: NCO-2015, NSQF/QP list, NIC-2008, LGD codes, PLFS tables, district boundaries | M | Reference tables populated and versioned (T) |
| FR-ING-04 | The system shall include a seeded synthetic telemetry generator (power, e-way bill, credit, commercial vehicle registrations per district per month) | M | Reproducible with a seed; every derived value carries `data_origin=synthetic` (T) |
| FR-ING-05 | The system shall provide an adapter interface (extract, validate, standardise) so a new source needs only configuration and a mapper | M | A sample new source added without changes outside adapter and registry (D/I) |
| FR-ING-06 | The system shall store every raw file immutably with checksum, load ID and timestamp | M | Altering a raw file is detected on the next run (T) |
| FR-ING-07 | The system shall support manual runs via CLI and scheduled runs (at least monthly) | M | Both paths produce the same output for the same inputs (T) |
| FR-ING-08 | Ingestion shall be idempotent | M | Re-running a load creates no duplicate rows (T) |
| FR-ING-09 | The system shall support backfill of past periods with the parameter set valid at that time or a chosen one | F | Backfilled run reproduces the historical snapshot (T) |
| FR-ING-10 | The system shall support live API/SFTP connectors for restricted sources when agreements exist | F | Connector contract tests pass with recorded fixtures (T) |
| FR-ING-11 | Authorised users shall be able to upload bulk files through the UI with a validation preview | F | Invalid file rejected with a reason before any load (T) |

| ID | Requirement | Pri | Acceptance / verification |
| --- | --- | --- | --- |
| FR-DQ-01 | The system shall validate schema, types, ranges, uniqueness, referential integrity and freshness using configurable rules | M | Seeded bad rows are all caught (T) |
| FR-DQ-02 | Failing records shall be quarantined with a reason code and never silently dropped | M | Input rows = loaded rows + quarantined rows (T) |
| FR-DQ-03 | The system shall flag anomalies (robust z-score above a configurable threshold, default 4) | M | Injected spike flagged, not deleted (T) |
| FR-DQ-04 | The system shall produce a quality report per load (rows in, loaded, quarantined, share mapped) | M | Report visible in UI and API (D) |

| FR-DQ-06 | The system shall show source health (fresh, stale, missing) with last successful load time | M | Stale source shown within one run cycle (D) |
| FR-DQ-07 | The system shall suppress or merge cells below a configurable small-count threshold in all outputs | M | No output cell below threshold in API or exports (T) |

| ID | Requirement | Pri | Acceptance / verification |
| --- | --- | --- | --- |

### 3.4 Demand index and forecasting (FR-FC)

| ID | Requirement | Pri | Acceptance / verification |
| --- | --- | --- | --- |
| FR-FC-01 | The system shall compute the CDI per district × trade × horizon (3, 6, 12 months) | M | All cells present for the pilot scope (T) |
| FR-FC-02 | All signal tiers shall be converted to workers per year before fusion | M | Unit test on each tier conversion (T) |
| FR-FC-03 | Postings-based demand shall be adjusted by a published, per-source coverage factor | M | Factor visible in the methodology page and run manifest (I) |
| FR-FC-04 | The system shall nowcast sector output change from telemetry signals using the approved parameter set | M | Golden-file regression on a reference district (T) |
| FR-FC-05 | The system shall apply the Leontief expansion `(I − A)⁻¹` and reject parameter sets where `ρ(A) ≥ 1` or the inverse has negative entries | M | Invalid set rejected at approval (T) |
| FR-FC-06 | The system shall convert sector requirements to occupations with location-quotient localisation | M | Sum of occupation demand reconciles to sector demand within tolerance (T) |
| FR-FC-07 | Fusion weights shall come from the approved parameter set and be renormalised when a tier is missing | M | Removing a tier changes weights and lowers confidence (T) |
| FR-FC-08 | The system shall apply small-area shrinkage to sparse districts | M | Sparse-district variance lower than without shrinkage on test data (A/T) |
| FR-FC-09 | The system shall produce P10/P50/P90 using at least 200 Monte Carlo draws | M | P10 ≤ P50 ≤ P90 for every cell (T) |
| FR-FC-10 | The system shall assign High/Medium/Low confidence with machine-readable reasons | M | Reasons present for every Low cell (T) |
| FR-FC-11 | The system shall store an explanation payload per cell (tier and signal contributions, supply components) | M | Contributions sum to the fused demand (T) |
| FR-FC-12 | Computation shall be deterministic: same inputs and parameter set produce an identical output hash | M | Two runs yield equal hashes (T) |
| FR-FC-13 | Every run shall store a manifest: parameter set ID, code revision, input load hashes, output hash, timings | M | Manifest retrievable by run ID (T) |
| FR-FC-14 | The system shall run a basic backtest on provided data and display its metrics labelled "on provided data" | S | Metrics page shows WAPE and rank correlation (D) |
| FR-FC-15 | The system shall monitor drift in inputs and residuals and block publishing on severe drift | F | Injected drift blocks publish (T) |
| FR-FC-16 | No computation path shall call an external ML or LLM service | M | Network egress test during a run shows no outbound calls (T) |

### 6.2 Data quality rules (defaults)

| Rule | Default |
| --- | --- |
| Required fields | Non-null district, period, value for every observation |
| Range | Non-negative counts; growth rates within ±300% flagged for review |
| Duplicates | One value per (source, district, signal, period); duplicates quarantined |
| Freshness | Stale after 1.5 × expected cadence; missing after 3 × |
| Mapping | At least 90% of records mapped per source; otherwise warning, below 75% blocks publishing |
| Small cells | Counts below 10 suppressed or merged |

## 7. Business Rules

| ID | Rule |
| --- | --- |
| BR-01 | Gap = Demand − Supply. Severity = Gap / max(Demand, ε), clipped to \[−1, +1\]. Positive means shortage. |
| BR-02 | Bands (defaults, configurable): Critical shortage ≥ +0.30; Shortage watch +0.15 to +0.30; Balanced between −0.15 and +0.15; Approaching saturation −0.30 to −0.15; Critical oversupply ≤ −0.30. |
| BR-03 | Confidence defaults: High at 0.75 or above; Medium 0.50 to 0.75; Low below 0.50. |
| BR-04 | An alert needs the band to hold for two consecutive runs, or a jump of two bands between runs. |
| BR-05 | Roll-ups sum headcounts, then recompute severity. |
| BR-06 | Displayed headcounts are rounded to the nearest 10 above 1,000 and shown with the P10-P90 range; exports carry exact model values with the same label. |
| BR-07 | Any value derived from synthetic data shows the synthetic badge in the UI, API and exports. |
| BR-08 | Simulation outputs never overwrite or mix with published values. |
| BR-09 | The "data as of" date is the latest period for which every required source is available, not the run date. |
| BR-10 | Horizons are measured from the end of the latest complete period. |
